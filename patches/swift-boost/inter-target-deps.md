# swift-boost: Inter-Target Dependency Fix

**Date**: 2025-03-24
**Status**: Proposed
**Repo**: https://github.com/21-DOT-DEV/swift-boost

## Problem

swift-boost exposes each Boost module as a separate SPM target, but declares no inter-target dependencies:

```swift
targets: boostModules.map { .target(name: $0) }
```

When a consumer depends on just `multi_index`, SPM only provides that target's headers. But `multi_index`'s headers `#include` from `config`, `core`, `preprocessor`, etc. — causing "file not found" errors.

Consumers must work around this by listing all transitive dependencies manually. For example, swift-bitcoin needs 27 of 35 modules just because `multi_index` and `signals2` transitively include them.

## Solution

Replace the flat target generation with dependency-aware targets using a dependency map.

### Change

```swift
// Before:
targets: boostModules.map { .target(name: $0) }

// After:
targets: boostModules.map { mod in
    .target(
        name: mod,
        dependencies: (boostDependencies[mod] ?? []).map { .target(name: $0) }
    )
}
```

## Complication: Circular Dependencies

SPM does not allow circular target dependencies. The dependency map contains cycles:

- `detail` → `utility` → `detail`
- `detail` ↔ `static_assert`
- `type_traits` → `detail` → `type_traits`

### Circular Foundation Group

These four modules form a tightly coupled foundation layer:

```
config ← static_assert ↔ detail ↔ utility
                ↕            ↕
            type_traits ←────┘
```

### Option A: Merge into a single target (recommended)

Merge the circular modules (`config`, `detail`, `static_assert`, `type_traits`, `utility`) into a single `boost_foundation` target. All other modules depend on `boost_foundation` instead of the individual pieces.

**Pros**: Clean, no workarounds, standard SPM pattern.
**Cons**: Consumers can't depend on just `config` — they get the whole foundation. (This is fine in practice since these are all header-only and tightly coupled.)

### Option B: Break cycles with headerSearchPath

Keep individual targets but use `cxxSettings: [.headerSearchPath(...)]` for the circular edges. Declare proper `dependencies:` for everything else.

```swift
// Example: detail depends on utility for headers, but declares it via headerSearchPath
// to avoid the circular dependency
.target(
    name: "detail",
    dependencies: ["config", "static_assert", "type_traits"],
    cxxSettings: [.headerSearchPath("../utility/include")]  // breaks cycle
),
```

**Pros**: Minimal change, preserves individual targets.
**Cons**: Partial workaround — the headerSearchPath edges don't trigger SPM to build/fetch those targets transitively for downstream consumers.

### Recommendation

**Option A** is cleaner. The foundation modules are always needed together anyway. The merged target would contain:

| Module | Purpose |
|--------|---------|
| `config` | Platform/compiler detection macros |
| `detail` | Internal implementation helpers |
| `static_assert` | Compile-time assertion macros |
| `type_traits` | Type introspection traits |
| `utility` | Common utility components |

## Consumer Impact

After this fix, swift-bitcoin's `Package.swift` simplifies from 27 explicit modules to just 2:

```swift
// Before (workaround):
let boostModules: [String] = [
    "assert", "bind", "config", "container_hash", "core", "describe",
    "detail", "foreach", "function", "integer", "iterator", "move",

    "throw_exception", "tuple", "type_index", "type_traits",
    "utility", "variant",

// After (proper deps):
.product(name: "multi_index", package: "swift-boost"),
.product(name: "signals2", package: "swift-boost"),
```

## Generation Script

The dependency map was generated by scanning headers:

```bash
BOOST_DIR="Sources"
for mod in $(ls -d "$BOOST_DIR"/*/ | xargs -I{} basename {} | grep -v BoostTest | sort); do
    deps=$(grep -rh '#include.*<boost/' "$BOOST_DIR/$mod/" 2>/dev/null | \
        sed -n 's|.*<boost/\([a-z_]*\)[/.].*|\1|p' | \
        sort -u | \
        while read dep; do
            if [ "$dep" != "$mod" ] && [ -d "$BOOST_DIR/$dep" ]; then
                printf '"%s", ' "$dep"
            fi
        done | sed 's/, $//')
    printf '    "%s": [%s],\n' "$mod" "$deps"
done
```

Re-run this script after adding/updating Boost modules to keep the map current.
